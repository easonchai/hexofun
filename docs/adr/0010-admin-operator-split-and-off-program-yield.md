# The pool has an admin and an operator, and the admin deploys principal off the program

> **2026-10-04: superseded by [ADR 0017](0017-live-yield-index-and-instant-withdraw.md)** for
> the off-program yield: `admin_withdraw` goes and the pool PDA holds the klend position. The
> Admin and Operator split, the two-step handover and the Pause asymmetry below stand.

One `authority` did everything: it cranked rounds from a hot keypair on a VPS and it was also the only key the program would trust with a parameter change. Adding real yield would have given that same key the power to move depositors' principal, which is not acceptable for real money on a box that runs a public API. `Pool` therefore gains `admin`, `operator` and `pending_admin`, and `authority` is removed. The admin holds `set_params`, `set_pause(false)`, `admin_withdraw`, `set_operator` and `propose_admin`; `accept_admin` is signed by `pending_admin`, so a handover takes two steps and a typo cannot hand the pool to an address nobody holds. The operator holds `create_round`, `settle_round`, `void_round`, `begin_epoch`, `close_registration`, `draw` and `rollover_epoch`, and owns the House Player. `payout` is permissionless, like `process_withdraw`: the winner and the destination are both fixed on chain, so gating it only gave the operator a way to veto a winner by sitting out `payout_timeout`. Pause is deliberately asymmetric: either key can stop the pool, only the admin can start it again, so a stolen hot key can cost a day of rounds but cannot reopen a pool the team has halted. On mainnet the admin is a Squads multisig, and the treasury and buyback reserve are whatever token accounts `create_pool` is given, which on mainnet are the multisig's associated token accounts.

Yield is earned outside the program. `admin_withdraw(amount)` sends principal to the admin's associated token account for `accepted_mint`, checked by address so a fat-fingered destination fails rather than lands, and it refuses unless `vault.amount - amount >= pool.pending_withdrawals`, so the admin cannot strand a depositor who has already requested their money. It does not touch `total_principal`: depositor claims are unchanged by where the USDC is sitting, and readers derive deployed principal as `total_principal - vault.amount` rather than trusting a stored number that a failed return could contradict. Bringing principal back is a plain SPL transfer to the vault with no instruction behind it, because there is nothing for the program to verify that the balance does not already say. The prize arrives the same way it always has, through the permissionless `fund_jackpot`, so funding is one signature from whatever wallet holds the harvested yield rather than a multisig vote; an epoch whose jackpot vault holds less than `min_jackpot` at close rolls over instead of paying out dust.

Considered and rejected: an on-chain yield adapter with a Kamino CPI. The program would carry a venue integration, price a receipt token, and need an upgrade every time the venue or its interface changed, and an audit of the pool would become an audit of the adapter. Doing it by hand is worse for trust and honest about it: the depositor is told the admin moves the money. The adapter stays possible later, because nothing a depositor signs would change.

Considered and rejected: keeping one key and gating principal moves behind a timelock. A timelock delays a theft, it does not prevent one, and the key still lives on the VPS. A multisig the attacker does not hold is the stronger answer for the same work.

Consequences: a depositor in the private beta trusts the admin and the lending venue as well as the code, so the README and the About page say that in plain words. Pulling principal and returning it are manual steps in the daily runbook, and a late return delays the payout of matured withdrawal requests, never the draw. `total_principal` stays the accounting truth while the vault balance shows what is actually home, so anyone can read how much is deployed. The layout change forces fresh pools on devnet and mainnet, and the upgrade authority moves to the multisig once the mainnet deploy is verified.

2026-09-28: `settle_round`, `void_round`, `draw` and `rollover_epoch` are permissionless (production-hardening ticket 01), the same reasoning as `payout` above: every precondition they check (status, `vrf_timeout`, fulfilled or unfulfilled randomness) is fixed on chain, so gating them only gave the operator a way to withhold a fulfilled result or leave a timed-out request stuck by sitting out the crank. The operator's remaining exclusive instructions are `create_round`, `begin_epoch` and `close_registration`.
